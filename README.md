# Custody

**Proving digital evidence has not been changed.**
ICSC 2026 Universities Hackathon, Track H.

Evidence is fingerprinted the moment it is collected in the field, every hand it passes
through is recorded in a tamper evident log, and any later change is provable and
localisable. The final output is a one page document a panel member or magistrate with no
technical background can read and act on.

This repository is the backend: the database, the custody chain, verification, and the PDF
report. The dashboard is in `hackathonWebApp`. The field app is in `hackathonMobile`.

---

## Where the data came from

**Everything in this system is synthetic and was generated by the team.** There are no real
persons, cases, accounts, student records, transactions or personal data of any kind. Names,
badge numbers, account numbers and phone numbers are invented. Account numbers are masked in
the style a real export would use, but the digits themselves are made up. The 30MB stand-in
for a phone extraction is random bytes from `/dev/urandom`; it is not a real extraction and
does not need to be, because the system fingerprints bytes and never interprets contents.

The test data pack lives in `custody-testdata/` and documents its own provenance.

---

## What it does

**The fingerprint.** At the moment of collection, on the collecting officer's own device,
before the file touches anything else, a SHA-256 fingerprint is taken. Any later verification
recomputes it and compares. Nothing between the scene and the server can alter the file
without it being detectable.

**The chain.** Every custody event stores the hash of the event before it, like beads knotted
onto a string. Change any event in the middle and every hash after it breaks, and we can
point at exactly where. There is a second chain at case level covering item creation, so that
deleting an entire item also leaves a trace.

**Chunked hashing.** Files are never hashed as one blob. A file is read in 4MB chunks, each
chunk is hashed, and a binary Merkle tree is built over the chunk hashes. Three things follow:
huge files can be hashed on a cheap field phone because memory use stays flat; when a file
changes we can say *which chunk* changed and therefore which byte range; and verification can
be paused and resumed after a power cut.

**Append only.** Custody events are never updated or deleted, and this is enforced by a
database trigger rather than by application code. A mistake is corrected by appending a
correction event that references the erroneous one, which is how physical evidence handling
already works.

### Why not a blockchain

A blockchain solves distrust between parties with no shared authority. A court or a
university panel has one. A hash chain plus append only storage plus periodically published
root hashes gives the same tamper evidence at a fraction of the complexity, and can be
explained to a panel member in a single sentence.

## Setup

Requires Node 20+ and PostgreSQL 16. Everything runs locally. Nothing is paid for, and
nothing needs a network.

### 1. PostgreSQL, natively, no Docker

```bash
# macOS
brew install postgresql@16
brew services start postgresql@16

# Ubuntu or WSL
sudo apt update && sudo apt install postgresql postgresql-contrib
sudo service postgresql start
```

Create the database and its owner. The `OWNER` clause matters: the `custody` user must own the
database for `CREATE TRIGGER` to succeed.

```bash
psql -h localhost -d postgres <<'SQL'
CREATE USER custody WITH PASSWORD 'custody' CREATEDB;
CREATE DATABASE custody OWNER custody;
SQL
```

Credentials are `custody/custody` deliberately. This is a local throwaway database holding
entirely synthetic data. We did not spend time on secrets management and would say so if asked.

### 2. The API

```bash
cd hackathonBackend
npm install
cp .env.example .env     # if .env is not already present
npm run demo:reset       # loads the schema, seeds, sets up the demo state
npm run dev
```

The server prints two addresses on startup. The second one is the laptop's address on the
local network and is what goes into the phone.

### 3. Verify the install

```bash
npm run test:acceptance
```

This runs the nine tests named in the test data pack, end to end, and leaves the system in the
clean demo state. Expect 23 passed, 0 failed.

**`TESTING.md` is the guide to all of it.** It is arranged as a ladder: each rung proves one
claim the pitch makes, and working up it in order is the fastest way to understand the system.
Start there rather than here if you are new to the project.

## Known install problems

**Peer authentication on Ubuntu.** `psql -U custody` can fail with a peer auth error even with
the right password. Add `-h localhost` to force TCP instead of a unix socket. If that still
fails, change the `local` line in `pg_hba.conf` from `peer` to `md5` and restart.

**WSL does not autostart PostgreSQL.** After every Windows reboot you need
`sudo service postgresql start`. If the presenting machine runs WSL, put that at the top of the
demo checklist. A refused connection ninety seconds before presenting is an avoidable way to
lose the room.

**localhost on a phone means the phone.** The field app must be given the laptop's LAN address.
The server binds `0.0.0.0` so that this works.

## API

```
GET    /api/health                     liveness, used by the field app's status dot

POST   /api/cases                      create case
GET    /api/cases                      list cases with integrity summary
GET    /api/cases/:id                  case detail with items
GET    /api/cases/:id/verify           case level chain, catches a deleted item

POST   /api/items                      seal a new evidence item (metadata only)
POST   /api/items/:id/deposit          record that the exhibit reached the store
GET    /api/items/:id                  item detail
GET    /api/items/:id/chain            full custody trail, with the break located
GET    /api/items/:id/verify           recompute and compare
GET    /api/items/:id/chunks           per chunk status, for the chunk map
GET    /api/items/:id/report           generated PDF report

POST   /api/custody/events             record a single custody event
POST   /api/custody/sync               batch upload a field device's queue

GET    /api/actors                     list officers
POST   /api/actors                     create officer
```

Items are addressable by UUID or by reference, so `/api/items/EX-2026-0007/verify` works.

### Sealing and depositing are two different acts

A field device seals an item at the scene: it records the fingerprint, the collector, the
times and the place. It cannot record where the exhibit will live, because it knows nothing
about the evidence store's layout. So a freshly synced item verifies as `awaiting_file`, which
is a different statement from `missing`:

| State | Meaning |
|---|---|
| `intact` | the file in the store matches the fingerprint taken at collection |
| `altered` | it does not, and we name the chunk and the byte range |
| `awaiting_file` | the fingerprint is recorded, the exhibit has not reached the store yet |
| `missing` | the exhibit was in the store and is no longer there |

`POST /api/items/:id/deposit` records the arrival, appends a custody event for it, and from
then on the item verifies normally. Collapsing these into one red result would accuse somebody
of losing evidence that had simply not arrived.

### Evidence files are never uploaded

The field app hashes on device and sends only metadata: root hash, ordered chunk hash array,
size, description, collector, timestamps. The file itself stays on the collection device or is
copied to the evidence store separately. This sidesteps request body limits entirely and is
closer to how real evidence handling works, where the exhibit goes to the store and the
paperwork goes to the registry.

### The server does not trust the client

On sync the server stamps its own `server_time` and recomputes every `event_hash` from the
event's own fields rather than trusting the client's. A device cannot know the server's item
and actor ids before the item exists, so the field app deliberately does not send event
hashes at all: the phone claims, the server records. A supplied hash that disagrees, or a root
hash inconsistent with its own chunk hashes, rejects the batch with 409.

## The offline timestamp problem, handled honestly

Offline events carry the device clock, which a defence could challenge. We do not hide this.
On sync the server records its own time, and the report shows both:

> Recorded on the officer's device at 14:32 on 3 Mar 2026, when the device had no network.
> Confirmed by the server 4 hours and 35 minutes later, at 19:07, once the connection was
> restored. Both times are shown because the device clock is set by the device and is not
> independently verified.

This is a deliberate design decision, not an oversight.

## Demo scripts

Live in `custody-testdata/scripts/`, driven from here by `scripts/reset-demo.sh`.

| Script | What it does |
|---|---|
| `make-large-file.sh` | generates the 30MB stand-in extraction |
| `tamper-file.js` | flips one byte at a chosen offset and prints the chunk index |
| `tamper-event.sql` | edits a custody event, breaking the chain at seq 2 |
| `delete-item.sql` | removes an item outright, caught by the case chain |
| `reset-demo.sh` | restores a clean, identical demo state |

The append only trigger is disabled deliberately inside the two SQL scripts. The escape hatch
exists on purpose: the demo depends on being able to tamper with the events table to show the
chain breaking.

`reset-demo.sh` keeps pristine copies of the evidence in `custody-testdata/.pristine/` and
restores from them. It does not "tamper again", because `tamper-file.js` XORs a byte with
`0xff` and is therefore its own inverse: a reset built on re-tampering drifts, and after two
resets the demo item is the wrong way round.

## Tests

```bash
npm test                 # parity, every endpoint, the sync path, the field app
npm run test:web         # the dashboard as a browser receives it
npm run test:acceptance  # the nine tests from the test data pack, end to end
```

`npm test` needs the API running. `test:web` needs the dashboard too. Between them they make
239 assertions.

| Suite | Covers |
|---|---|
| `device-parity` | the field app's hashing against the server's, byte for byte |
| `api` | all sixteen endpoints, response shapes, error paths, injection attempts |
| `sync` | a device that collected offline and synced later |
| `mobile` | the field app's own payload builder, imported, against the live API |
| `web` | every dashboard route, rendered output, the broken chain, the 404s |
| `acceptance` | the nine tests named in the test data pack |

`test/device-parity.test.mjs` is the one that must not be allowed to rot. It transliterates the
Expo app's hashing into Node and asserts it produces byte-identical chunk hashes, Merkle roots
and event hashes to the server, including odd node promotion at 1, 2, 3, 5, 7, 8 and 9 chunks.
If these two implementations ever drift, every fingerprint ever taken in the field becomes
unverifiable.

## Deploying to Render

The live presentation should run against the **local** PostgreSQL on the presenting laptop.
The whole pitch is that collection works when the network dies, and demonstrating offline
first architecture against a cloud database is a contradiction a judge will notice. Hackathon
wifi will also fail at the worst possible moment. This deployment is for sharing the dashboard
and the reports outside the room.

`render.yaml` provisions a web service and a free PostgreSQL instance. After the first deploy,
run once from the Render shell:

```bash
npm run deploy:setup
```

That generates the 30MB stand-in, loads the schema and seeds the synthetic data, in that
order, because the seeder fingerprints each evidence file as it finds it.

Three things this repository does so that hosting works at all:

- **The evidence pack is vendored** at `testdata/`, so the service can verify the files it is
  asked about without depending on anything outside its own checkout. `EVIDENCE_ROOT` defaults
  there.
- **TLS is enabled for remote databases only.** A managed database presents a certificate this
  process has no root for; a local socket needs no TLS and silently enabling it breaks the demo
  machine. The connection string decides.
- **The port comes from the environment**, and the server binds `0.0.0.0`.

Render's free tier has an ephemeral filesystem, so the 30MB file and any deposited exhibit are
lost on redeploy. Re-run `npm run deploy:setup` afterwards. The custody chain itself lives in
the database and survives.

## Honest limits

Every one of these is true and we state them openly.

- **Corrupt collector.** If the collecting officer tampers before sealing, we prove the
  integrity of already tampered evidence. We protect the chain from the moment of collection
  onward, not before it. This is a real and unsolved limit.
- **Device clock.** Offline timestamps come from the device and can be wrong or deliberately
  set. We show both device and server time rather than hiding the gap, but the device time is
  not independently trustworthy.
- **Scale.** We tested at 30MB and extrapolated to 100GB. We did not test a full phone
  extraction. What we can defend is that memory use stays flat as the file grows, because we
  never hold the whole file at once. Measured heap growth while hashing the 30MB file was
  under a megabyte.
- **Per officer signing.** Events are attributable to a login, not cryptographically to a
  person. Signing each event with an officer held key is the correct upgrade. We describe it;
  we did not build it.
- **Storage.** We assume the evidence file itself is retained somewhere. We prove change, we do
  not prevent deletion of the underlying file. A deleted file verifies as `missing`.
- **Bulk compromise.** An attacker with full database and server access could rebuild the
  entire chain consistently. Publishing periodic root hashes to an external location is the
  mitigation. We describe it; we did not build it.
- **Dependency advisories.** `npm audit` reports advisories in the Next.js dev server and its
  image tooling. This is a local only demonstration on synthetic data and we chose not to take
  a forced major upgrade days before presenting.
